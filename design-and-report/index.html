Project 23: Telegram Bot Automated KPI Reporting

Tujuan project: membangun pipeline yang setiap pagi menghitung KPI produksi (yield, NG rate, rework rate per stasiun) lalu mengirim ringkasan dan grafiknya ke Telegram, serta mengirim alert saat yield turun di bawah ambang, sehingga supervisor tahu kondisi lini tanpa menunggu laporan manual.

Kategori:Rancangan projectPerakitan sepeda motorData simulasiPython + bot otomatis

Project Introduction

Bayangkan aplikasi cuaca di HP. Setiap pagi aplikasi mengirim ringkasan: suhu, peluang hujan, dan grafik kecil. Jika ada badai, aplikasi langsung mengirim peringatan. Kita tidak perlu membuka situs cuaca dan membaca tabel panjang setiap hari.

Banyak pabrik masih bekerja seperti sebelum ada aplikasi cuaca: seseorang mengunduh data, menyusun laporan di Excel, lalu mengirimnya manual ke grup chat. Jika ada masalah di malam hari, kabarnya baru sampai keesokan siang.

Project ini membangun pipeline laporan otomatis: data produksi dihitung menjadi KPI dengan SQL, dibuat grafiknya, lalu dikirim lewat bot Telegram sesuai jadwal. Fokusnya tetap analisis dan aturan KPI; bot hanya lapisan pengiriman. Datanya adalah data simulasi karena data pabrik bersifat rahasia. Kata bergaris bawah putus-putus kuning bisa diklik untuk melihat artinya.

Lini produksi bisa dibayangkan sebagai tiga jalur yang berjalan bersamaan. Dua jalur pertama sudah ada di pabrik. Jalur ketiga adalah yang dibangun di project ini.

1. BackgroundKenapa tema ini dipilih

Latar belakang masalah

Di banyak lini produksi, laporan KPI harian disusun manual. Seseorang mengunduh data, menghitung di Excel, membuat grafik, lalu mengirimnya ke grup chat. Akibatnya:

  • Laporan harian memakan waktu setiap pagi, dan tertunda jika penyusunnya cuti atau sibuk.
  • Masalah di shift malam baru diketahui siang hari, saat laporan sampai.
  • Format dan rumus laporan bisa berbeda antar penyusun.
  • Tidak ada aturan jelas kapan sebuah penurunan yield perlu segera dilaporkan.

Alasan memilih tema ini sebagai portofolio

  • Dekat dengan pekerjaan sehari-hari. Menyusun laporan output, yield, dan rework adalah rutinitas Process Engineer, sehingga kebutuhan pengguna sudah dipahami.
  • Menunjukkan skill otomatisasi pelaporan. SQL untuk KPI, grafik otomatis, aturan alert yang dievaluasi dengan data, penjadwalan, dan pengelolaan secret.
  • Tingkat kesulitan sulit. Perhitungannya deskriptif, tetapi pipeline harus andal dan berjalan sendiri setiap hari: data terlambat, data kosong, dan kegagalan kirim harus ditangani.
  • Memakai ulang project lain. Struktur tabel dan definisi KPI mengikuti Project 3 (Yield, Rework & Defect Tracking). Bot bisa membaca hasil Project 27 (Analytics Engineering Mini-Warehouse).

4. DatasetData produksi simulasi buatan sendiri, ditambah log pengiriman bot

Kenapa data simulasi? Data pabrik bersifat rahasia, dan pesan bot tidak boleh berisi data perusahaan. Program Python membuat data produksi dengan struktur Project 3 dan menanam kejadian yang harus ditangkap alert.

Ukuran: 10 stasiun, 3 model, 2 shift, sekitar 75 hari kerja. Perkiraan ±4.500 baris produksi harian dan ±6.000 baris defect. Log pengiriman bertambah satu baris untuk setiap pesan.

Sumber data: data simulasi buatan sendiri, dibuat oleh skrip scripts/generate_data.py di repositori project (Versi: v1, rancangan; Tanggal dibuat: saat Tahap B dikerjakan). Tidak memakai dataset publik atau data perusahaan.

Fakta yang sengaja ditanam (ground truth)

1. Tiga kejadian penurunan yield: 2 hari di Engine Assembly, 1 hari di Frame Painting, dan penurunan perlahan selama ±1 minggu di Roller Test.

2. Dua hari data terlambat masuk (baru tersedia siang hari).

3. Satu hari data kosong sama sekali.

4. Satu lonjakan NG pada satu defect yang tidak menurunkan yield lini secara besar, untuk menguji aturan lonjakan NG.

5. Sekitar 2–3% data kotor: jumlah negatif, OK + NG lebih dari input, baris ganda.

9. Assumptions & LimitationsKomponen tambahanKeputusan yang sudah diambil dan hal yang perlu diwaspadai

Jenis data: simulasi Sudah Anda setujui

Data produksi dibuat program dengan struktur Project 3. Pesan bot hanya dikirim ke grup demo.

Konteks: perakitan sepeda motor Sudah Anda setujui

Halaman publik memakai lini perakitan sepeda motor dengan 10 stasiun dan 3 model. Struktur tabel tetap sama dengan Project 3.

Tools: DuckDB + Streamlit Sudah Anda setujui

Konsisten dengan project lain. Tools khusus dari daftar portofolio (python-telegram-bot, matplotlib, GitHub Actions) tetap dipakai. Streamlit dipakai untuk dashboard pendamping.

Ruang lingkup Usulan awal

Satu grup Telegram, satu laporan harian pukul 07.00, alert dicek sekali sehari. Belum real-time per jam. Dampak dihitung dalam menit kerja, belum dalam rupiah. Tingkat kesulitan: sulit.

Hal yang perlu diwaspadai Usulan awal

Alert terlalu sering membuat orang abai. Ambang dipilih dari data, dan jumlah alert palsu dilaporkan terbuka.

Jadwal cloud bisa terlambat. GitHub Actions kadang menunda jadwal beberapa menit. Waktu kirim aktual dicatat di delivery_log.

Keamanan data. Di dunia nyata, data perusahaan yang dikirim ke aplikasi chat perlu izin perusahaan. Project ini hanya memakai data simulasi.

Pola belum tentu penyebab. Alert menunjukkan kapan yield turun, bukan kenapa. Investigasi tetap dilakukan di lapangan.

2.5 Aturan lonjakan defect Q6

7. KesimpulanHasil analisis, Impact, success criteria, rekomendasi, saran perbaikan, dan batasan

7.1 Hasil analisis: jawaban atas pertanyaan utama

Bagaimana mengirim ringkasan KPI harian (yield, NG rate, rework rate per stasiun) beserta grafik ke Telegram secara otomatis, dengan alert yang menangkap masalah nyata tanpa terlalu banyak alarm palsu?

  • Laporan harian: pipeline menghitung KPI dari view SQL, menyusun pesan dengan grafik, dan mengirimnya lewat pengirim yang bisa diganti. Pada replay 74 hari, 74 laporan harian dan 8 alert dibuat dalam mode dry-run. Pengiriman ke Telegram sungguhan belum dilakukan.
  • Alert yang menangkap masalah nyata: yield lini di bawah rata-rata 20 hari − 2,0σ (R1) dan yield stasiun di bawah rata-rata − 3,5σ (R2) menangkap ketiga penurunan dengan 0 alert palsu; R3 (lonjakan defect) 11 benar dari 12. Ambang tetap menghasilkan 5 alert palsu.
  • Keandalan: 95,8% tepat waktu bila data sudah ada; data terlambat dan kosong ditangani dengan pemberitahuan, cek ulang tiap jam, dan batas 14:00.
  • Angka benar: 12 dari 12 tanggal sampel sama di pesan, SQL, dan Excel.

7.2 Impact

  • Nilai praktis (estimated): sekitar 28 menit per laporan, atau 114 jam kerja per tahun, bila penyusunan manual memang sekitar 30 menit. Alert datang di pagi hari berikutnya, sekitar 4 jam lebih awal daripada laporan manual yang sampai siang (asumsi).
  • Nilai analitis: pemilihan ambang dari data menunjukkan bahwa ambang tetap tampak masuk akal tetapi menghasilkan banyak alarm palsu, dan bahwa evaluasi yang melewatkan masa pemanasan terlalu optimistis.
  • Nilai portofolio: pipeline lengkap dari data simulasi dengan ground truth sampai bot dry-run, evaluasi alert, uji skenario, cek silang tiga sumber, dashboard, dan notebook.
  • Belum terukur: dampak pada supervisor nyata, jumlah alarm yang diabaikan, dan waktu tanggap. Tidak ada data pabrik.

7.4 Rekomendasi

  • Pakai batas yang mengikuti rata-rata 20 hari (R1 dan R2) sebagai alert utama, bukan ambang tetap; kirim R3 sebagai informasi tambahan karena presisinya 92%.

  • Tetap kirim pesan walau data hilang: pemberitahuan "belum masuk" dan pesan akhir pukul 14:00 membedakan lini aman dari pipeline rusak.

  • Ukur waktu penyusunan laporan manual dengan stopwatch pada beberapa hari, dan ukur jeda serta kegagalan GitHub Actions dari beberapa minggu run nyata.
  • Hubungkan handle() ke polling Telegram dan tambah screenshot pesan nyata; tambah alert per jam untuk kejadian yang tidak perlu menunggu pagi.
